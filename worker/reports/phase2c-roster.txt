## Route list (exact paths, as mounted)

1. GET /api/meeting/roster — meeting_controller session; reads meeting_types code='sup' (missing -> 400 ประเภทการประชุมไม่ถูกต้อง); reads meeting_roster for that type with is_active=true joined to employees (employee_code, full_name, departments(name), positions(name)); responds { ok:true, count, members:[{employeeId, employeeCode, fullName, departmentName, positionName}] } sorted by Thai collation. Read failure -> 500 ไม่สามารถบันทึกได้ กรุณาลองใหม่.
2. GET /api/meeting/roster/search?q= — normalizeSearchQuery; shorter than 2 characters answers { ok:true, results: [] } with no database call; otherwise reads the active sup roster ids, then searches active employees by full_name OR employee_code with a single encoded PostgREST or=(full_name.ilike.*,employee_code.ilike.*) filter, limit 10; merges and dedupes by employee id, drops roster members, sorts Thai, caps at 10; responds { ok:true, results:[...] }. The or-filter value is URL-encoded and parentheses are additionally encoded to %28/%29 so the or=() structure cannot be broken. Read failure -> 500 with the save message.
3. POST /api/meeting/roster/add — strict body { employeeId } (single string key, UUID pattern matching Express z.uuid(): versions 1-8 with RFC variant, nil and max UUID, case-insensitive like zod) else 400 ข้อมูลไม่ถูกต้อง; verifies the employee exists and is_active -> otherwise 400 ไม่พบพนักงานที่ใช้งานอยู่; needs both sup and monthly types -> otherwise 400 ประเภทการประชุมไม่ถูกต้อง; upserts meeting_roster rows for BOTH types on conflict (meeting_type_id,employee_id) with is_active=true, created_by = controller employee id, created_at = now ISO; responds { ok:true }. No audit row.
4. POST /api/meeting/roster/remove — strict body { employeeId } as add; sets is_active=false for that employee on both types (patch with return=representation to count matched rows); zero updated rows -> 404 ไม่พบรายชื่อนี้; otherwise { ok:true }. No audit row.

Common: every route sets Cache-Control: no-store and requires a valid meeting_controller hr_session cookie; 401 ไม่ได้เข้าสู่ระบบ without a usable session, 403 ไม่มีสิทธิ์เข้าถึงส่วนนี้ for the wrong role. Logs write only { name, code } from errors; no tokens, cookie values, hashes, employee national IDs or request/response bodies appear in logs or responses.

## Known differences from Express (to decide later)

- Add re-add behavior: Express overwrites created_by and created_at on re-add (its upsert sends the full row). The Worker does the same on purpose; if the intent is "keep the original creator on re-add", change the loop to omit created_by/created_at on existing rows. Flagged as a deliberate retention of the current Express behavior; decision deferred.
- Search is one query instead of two: Express runs two ilike queries (name and code) and merges in code; the Worker sends a single or=(...) filter and merges by id. Results are equivalent up to row selection with limit; PostgREST applies limit server-side without an order clause, just like the Express queries, so which first-10 rows a database returns is not deterministic in either implementation.
- Search short-circuit: normalization and the >= 2 check happen before any database call in both implementations (same visible behavior).
- The search route reads q through an explicit new URL(...).searchParams lookup instead of Hono's c.req.query(), which this Hono version leaves undecoded for %-escaped values; behavior matches the Express req.query parsing.

----------------------------------
Same fixture, same frozen clock (2026-01-05T05:30:00Z, Monday 12:30 Bangkok),

its own in-memory store through a fake client/fetch. Full detail is in

  table               Express   Worker   identical
  meeting_attendance  8 rows    8 rows   yes
  audit_logs          2 rows    2 rows   yes
  meeting_sessions    3 rows    3 rows   yes

  Compared fields: attendance session_id, employee_id, status_code, reason,

Scenario 2 (sup-session creation path, weekday Monday after the cutoff):

  table               Express   Worker   identical
  meeting_sessions    1 row     1 row    yes (sup-2026-01-05, 09:00 / 12:00)
  meeting_attendance  2 rows    2 rows   yes
  audit_logs          1 row     1 row    yes (detail {"count":2})

Only difference, allowed by the task: insertion order inside a batch. Express
writes per session in database order, so its audit rows are count 4 then count 2;
the Worker sorts due sessions oldest first, so the same two rows arrive in the
reverse order. No column, reader or API depends on audit_logs insertion order.

Result: no difference in written rows or audit output. No stop condition.
The Phase 4a implementation was not changed.

A2. Cron vs the Express throttle
--------------------------------
Express (server/index.js 54-60, server/auto-absent-job.js):
- On boot, unless AUTO_ABSENT_ENABLED is exactly "false", startAutoAbsentJob()
  schedules one run 60 s later (FIRST_RUN_DELAY_MS) and then one every 10 minutes
  (RUN_INTERVAL_MS); both timers are unref'd.
- Each tick calls triggerAutoAbsentIfDue(), which asks shouldStartRun(): false if
  runInProgress, false if now - lastStartedAt < 10 min, otherwise it stamps
  lastStartedAt, sets runInProgress, runs, and clears the flag in finally.
- Three read routes also nudge it opportunistically: GET /api/meeting/dashboard,
  GET /api/meeting/overview, GET /api/register/context.

The throttle controlled only whether a run may start now. runAutoAbsentOnce()
takes no throttle input and touches neither variable, so no query, row or audit
value ever depended on it.

Why cron does not change behaviour: one cron event is one run, spaced exactly 10
minutes, the same cadence the interval asked for, and there is no in-memory state
left to guard. Two timing nuances, neither a behaviour change:
- Express also ran once ~60 s after boot; the Worker first runs at the next
  10-minute boundary. Runs are idempotent, so only the start time moves.
- The request nudges disappear, so a session that becomes due just after a tick
  is picked up to one interval (<= 10 min) later than a request would have
  triggered it. The rows written are identical.
The throttle never protected a critical section beyond suppressing a redundant
run; even overlapping runs would store the same result because of the audit
marker and ignoreDuplicates.

Deviations and open questions
-----------------------------
a. KEEP_ALIVE_CRON is exported from src/keep-alive.js, not src/index.js: the
   Workers module runtime rejects a non-function named export from the entry
   module (same constraint found in Phase 4a).
b. The error log is one fixed string with an optional HTTP status; the error code
   is deliberately not logged, matching the task's "fixed message" wording.
c. Whether these reads actually count as Supabase activity is still unconfirmed
   (spec section 5). The owner has to check Dashboard -> Reports after a day of
   runs; no tool in this run may call the live project.
d. Deploying starts both triggers at once (approved decision 4). Phase 4b adds no
   flag, no alerting and no dashboard change.
e. workerd CPU for keep-alive was not measured: it is a single GET, and wrangler
   dev does not report CPU time. The auto-absent CPU numbers in
   phase4a-report.txt still stand as a Node proxy only.

PART B - BATCH RESET-CODE ISSUANCE DESIGN (document only, no code)
===============================================================================

Document: reports/batch-reset-code-design.md

Current behaviour summarised there from scripts/issue-reset-code.js: one employee per run,
voids that employee's unused codes (lines 51-57), inserts one row with a 60-minute expiry
(lines 59-75), writes audit action pin_reset_code_issued with actor ADM001 (lines 77-86),
and prints the code once to the terminal (lines 88-97). Nothing is written to disk.

Constraint that shapes every option: the script runs on the owner's machine, needs Supabase
service credentials and the same PIN_RESET_SECRET as the Worker, and a reset code is itself
a credential, so no log or shared file may contain one.

Recommendation: Option 1 (loop over the employee codes, one run per employee, codes read
from the terminal). It needs no code, adds no route that creates credentials, and cannot
leave a file of live codes behind. Option 2 (list file with optional encrypted export) is
worth it only for large batches and brings key management plus a deletion step; Option 3
(HR issues from a Worker page) is not recommended before cutover because it adds a
credential-creating route, needs its own authorization/rate-limit/audit design, and puts
codes through the browser and the Pages proxy.

Also documented: the audit identity gap (ADM001 is hardcoded in every option except the
new route, so no option records the real operator), the voiding rule (the batch must run
once per employee; a re-run silently kills the code already handed out), and six owner
decisions (who runs it, how codes reach staff, whether ADM001 stays the actor, batch scope,
whether file output is allowed, and whether a dry-run mode is added first).

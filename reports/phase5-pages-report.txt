2. What the Worker depends on from the request
---------------------------------------------
Searched worker/src for Host, Origin, Referer, APP_ORIGIN, CORS and CSRF.

  a. Host header: not read anywhere. No route builds an absolute URL from the
     request, and no redirect is derived from it (redirectTo values are app
     paths such as /pending?to=...). Forwarding the request URL unchanged is
     therefore safe.
  b. Origin / Referer: not read anywhere, and there is no CSRF token or
     same-origin check. The Worker also sets no Access-Control-* response
     headers, so the proxy needs no preflight handling and adds none.
  c. APP_ORIGIN (a Worker variable, not a header): read in
     src/routes/meeting.js at the types and qr/rotate handlers, and used by
     buildRegisterUrl() in src/meeting-window.js to build the QR register link.
     So the Worker never derives the public origin from the request; in
     production APP_ORIGIN must be the Pages origin. Locally it was set to
     http://127.0.0.1:8788 and the tests confirm the built link starts with that
     origin (check e6), i.e. the link follows configuration, not Host.
  d. Cookie: read from the Cookie request header in src/require-role.js and in
     the /api/auth/me and /api/auth/logout handlers. The proxy must (and does)
     forward Cookie unchanged.
  e. Content-Type and Content-Length: validated by the dashboard reason, roster,
     monthly-session, register and meeting handlers before parsing a JSON body.
     The proxy forwards both headers and streams the body unchanged, so those
     checks see exactly what the browser sent.
  f. CF-Connecting-IP: read by src/rate-limit.js. It is an ordinary request
     header on Pages, so it is forwarded like every other header.
  g. Response side: the Worker sets Set-Cookie (login/logout) and
     Cache-Control: no-store on several routes. The proxy returns the Worker
     response object itself, so both survive untouched.

Conclusion: the Worker needs no change to run behind the proxy, so the stop
condition "the Worker needs a code change" was not hit.

3. The proxy and its configuration
----------------------------------
functions/api/[[path]].js exports one onRequest handler (all methods, /api and
/api/*):

  - builds a Headers copy of the request, skipping the RFC 9110 hop-by-hop
    headers (connection, keep-alive, proxy-authenticate, proxy-authorization,
    te, trailer, transfer-encoding, upgrade) and nothing else, so Cookie,
    Content-Type, Content-Length, Accept, CF-Connecting-IP and Host are
    forwarded as sent;
  - constructs new Request(request.url, { method, headers, body, redirect:
    "manual" }) - the URL is the Pages URL, so path and query string cross the
    binding unchanged and a Worker redirect is passed to the browser instead of
    being followed;
  - sends it with env.WORKER.fetch(...) and returns that response object as-is
    (status, body and every Set-Cookie header untouched; nothing is rebuilt, no
    cookie is added, removed or rewritten);
  - returns a fixed 503 {"ok":false,"message":"service unavailable"} with
    Cache-Control: no-store when env.WORKER is missing or the fetch throws. The
    thrown error is swallowed, never logged into the response.

Configuration keys, verified against developers.cloudflare.com/pages:

  Local (used for the tests below, exact command):
    wrangler pages dev dist --ip 127.0.0.1 --port 8788 \
      --service WORKER=hr-workers-spike --compatibility-date 2026-09-01
    Binding name: WORKER. Script name: hr-workers-spike (worker/wrangler.toml
    "name"). Wrangler printed "env.WORKER (hr-workers-spike) Worker local
    [connected]", i.e. the binding reached the separately running local Worker.

  Production (not performed; one equivalent of the same binding):
    Pages project -> Settings -> Bindings -> Add -> Service binding,
    Variable name WORKER, Service hr-workers-spike.
    Or, if the project is switched to a Pages Wrangler config file:
      name = "hr-hub-web"
      pages_build_output_dir = "./dist"
      compatibility_date = "2026-09-01"
      [[services]]
      binding = "WORKER"
      service = "hr-workers-spike"

  Docs read for this step:
  - /pages/functions/bindings/ (Service bindings): "Service bindings enable you
    to call a Worker from within your Pages Function" and, for local work,
    "run the Worker you want to bind to via wrangler dev and in parallel, run
    wrangler pages dev with --service <BINDING_NAME>=<SCRIPT_NAME> where
    SCRIPT_NAME indicates the name of the Worker". The documented example call
    is "return context.env.SERVICE.fetch(context.request)".
  - /pages/functions/wrangler-configuration/: the Pages-only key is
    pages_build_output_dir, and using the file makes it the source of truth for
    the project - which is why no such file was added in this phase.
  - /pages/configuration/serving-pages/ (SPA rendering): "If your project does
    not include a top-level 404.html file, Pages assumes that you are deploying
    a single-page application ... serves the root (/) for any incoming path
    that does not correspond to a static asset."

SPA routing: no _redirects file is needed or shipped. A /* /index.html 200 rule
was tried first, but wrangler rejected it locally with "Infinite loop detected
in this rule and has been ignored", and with the rule removed the client routes
still answered 200 from the documented SPA default. The same behaviour covers
the QR deep link /meeting/register?t=... .

Open questions
--------------
a. The production binding is a dashboard setting (Settings -> Bindings ->
   Service binding, WORKER = hr-workers-spike) or requires adding the Pages
   Wrangler config file, which would then become the source of truth for the
   whole Pages project (including its variables). Neither was done: deploying is
   out of scope for this phase, and DEPLOY.md was not edited. Whoever deploys
   must pick one and record it there.
b. APP_ORIGIN must be the final Pages origin (or custom domain) on the Worker,
   otherwise QR register links point at the wrong host. It is a Worker variable,
   so it is set by the existing Worker deploy procedure, not by Pages.
c. The session cookie keeps Secure whenever COOKIE_SECURE is unset, which is
   correct on the HTTPS Pages origin; the local run needed COOKIE_SECURE=false
   and that flag must never be set in production.
d. No route sets more than one Set-Cookie today, so the "every Set-Cookie
   survives" property is guaranteed by returning the response object untouched
   rather than by a multi-cookie test; if a future route sets two, nothing in
   the proxy would need to change.
e. Pages' SPA default depends on the project having no top-level 404.html. If a
   404.html is ever added to public/, client routes and QR deep links would 404
   and a routing rule would be required again.
f. Local tests used fixed ports 8787/8788/8789 and a loopback fake; workerd CPU
   was not measured, and nothing here was exercised against a live edge.
